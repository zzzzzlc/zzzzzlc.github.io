# 如何提高系统稳定性：从故障预防到快速恢复的完整策略

## 一、问题来源

每个经历过线上故障的团队，都知道系统稳定性的分量：

**业务层面的痛点：**

- 大促/活动期间系统突然挂掉，用户投诉铺天盖地，直接损失 revenue
- 一个非核心功能（比如导出报表）把数据库打满，核心交易链路也跟着挂
- 第三方服务（支付网关、短信接口）不稳定，自己的系统被拖垮
- 发布新版本后线上出 bug，回滚不及时影响持续数小时

**技术层面的痛点：**

- 系统没有监控，故障是用户反馈后才知道的，MTTR（平均恢复时间）极长
- 服务之间没有熔断，一个下游服务超时，上游所有线程池被占满，引发雪崩
- 数据库没有限流，一个慢查询把连接池耗尽，整个系统不可用
- 不知道该做哪些稳定性建设，到处是风险点却不知从何下手

**核心问题：系统稳定性不是"出了问题再修"，而是一套从预防 → 检测 → 容灾 → 恢复的系统工程。**

本文将从故障预防、容灾设计、可观测性、发布安全、故障恢复五个维度，给出可落地的系统稳定性建设方案。

## 三、限流：守住系统的入口

### 3.1 为什么需要限流

```
不限流的后果：
- 突发流量打垮服务（大促、秒杀、爬虫攻击）
- 下游服务被压垮（数据库、缓存、第三方接口）
- 资源被个别用户/租户耗尽，影响其他用户

限流的目的：在系统承受能力之内，尽可能多地处理请求
```

### 3.2 限流算法对比

| 算法 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| 固定窗口 | 按固定时间段计数 | 简单易实现 | 窗口边界有突刺（两倍流量） | 低精度要求 |
| 滑动窗口 | 按滑动时间段计数 | 解决突刺问题 | 实现稍复杂 | 一般场景 |
| 漏桶 | 请求进入桶中，匀速流出 | 流量平滑 | 无法应对突发合理流量 | 需要匀速处理 |
| 令牌桶 | 匀速生成令牌，请求消耗令牌 | 允许一定突发 | 实现稍复杂 | 大部分场景（推荐） |
| 滑动日志 | 记录每个请求的时间戳 | 精确 | 内存开销大 | 分布式精确限流 |

### 3.3 限流实现方案

```
限流层级：

1. 接入层限流（Nginx / API 网关）
   - 按 IP / 用户 / 接口限流
   - 最外层防线，挡住大部分流量

2. 应用层限流（服务内）
   - 单机限流：Guava RateLimiter / 令牌桶
   - 分布式限流：Redis + Lua 脚本

3. 数据库层限流
   - 连接池大小控制
   - 慢查询 Kill
   - 最大并发查询数限制
```

```nginx
# Nginx 接入层限流
# 按 IP 限流：每个 IP 每秒最多 10 个请求
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;

server {
    location /api/ {
        limit_req zone=api_limit burst=20 nodelay;
        # burst=20：允许突发 20 个请求排队
        # nodelay：突发请求立即处理，不排队等待
        limit_req_status 429;  # 超出返回 429
    }
}
```

```lua
-- Redis + Lua 分布式令牌桶限流
-- 参数：KEYS[1]=限流key, ARGV[1]=桶容量, ARGV[2]=令牌生成速率(个/秒), ARGV[3]=当前时间戳

local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

local info = redis.call('HMGET', key, 'tokens', 'last_time')
local tokens = tonumber(info[1]) or capacity
local last_time = tonumber(info[2]) or now

-- 计算经过的时间，补充令牌
local elapsed = math.max(0, now - last_time)
tokens = math.min(capacity, tokens + elapsed * rate)

if tokens >= 1 then
    tokens = tokens - 1
    redis.call('HMSET', key, 'tokens', tokens, 'last_time', now)
    redis.call('EXPIRE', key, math.ceil(capacity / rate) * 2)
    return 1  -- 允许
else
    return 0  -- 拒绝
end
```

```
按场景选择限流维度：

┌──────────────────┬─────────────────────────┐
│       场景       │       限流维度          │

│ 防 DDoS/爬虫     │ 按 IP 限流              │

└──────────────────┴─────────────────────────┘
```

## 四、熔断：防止故障雪崩

### 4.1 为什么需要熔断

```
没有熔断的连锁反应：

服务 A 调用服务 B（耗时 200ms → 开始超时）
  → A 的线程等待 B 响应，线程池逐渐耗尽
    → A 无法处理新请求，上游服务 C 调用 A 也开始超时
      → C 的线程池也耗尽
        → 整个调用链雪崩

熔断的作用：
当 B 不可用时，A 快速失败（返回默认值或错误），而不是傻等
→ 释放线程资源 → A 仍然可以处理其他请求 → 阻止雪崩
```

### 4.2 熔断器状态机

```
                 ┌─────────────┐
     成功率恢复   │             │  连续失败达阈值
    ┌────────────│    半开      │────────────┐
    │            │  (Half-Open)│            │
    │            └──────┬──────┘            │
    │                   │                   │
    │          试探请求成功                   │
    │                   │                   ▼
    │            ┌──────┴──────┐      ┌──────────┐
    │            │    关闭      │      │   打开    │
    └────────────│  (Closed)   │      │ (Open)   │
                 └─────────────┘      └────┬─────┘
                                           │
                                    冷却期过后
                                     自动转入半开

状态说明：
- Closed（关闭）：正常状态，请求正常通过
- Open（打开）：熔断状态，请求被直接拒绝，返回降级响应
- Half-Open（半开）：试探状态，放少量请求通过，判断下游是否恢复
```

### 4.3 熔断配置参数

```
核心参数：

1. 失败阈值（failure threshold）
   - 触发熔断的最低失败率（如 50%）
   - 或触发熔断的最低失败次数（如 10 次失败/分钟）

2. 时间窗口（time window）
   - 统计失败率的时间窗口（如 10 秒）
   - 窗口太小容易误判，太大反应迟钝

3. 冷却期（cooldown / sleep window）
   - 熔断打开后保持多久进入半开状态（如 30 秒）

4. 半开试探数（half-open max requests）
   - 半开状态下允许通过的试探请求数（如 5 个）

5. 慢调用阈值（slow call threshold）
   - 不仅按失败率熔断，也可以按慢调用比例熔断
   - 如：响应时间 > 3 秒的请求占比 > 80% 则熔断
```

### 4.4 代码示例

```typescript
// 使用 resilience4j（Java）或自定义熔断器

interface CircuitBreakerConfig {
  failureRateThreshold: number;    // 失败率阈值，如 50
  slowCallRateThreshold: number;   // 慢调用率阈值，如 80
  slowCallDurationThreshold: number; // 慢调用判定时间(ms)
  slidingWindowSize: number;       // 滑动窗口大小
  minimumNumberOfCalls: number;    // 最小请求数（低于此数不计算失败率）
  waitDurationInOpenState: number; // 熔断打开持续时间(ms)
  permittedNumberOfCallsInHalfOpen: number; // 半开试探数
}

class CircuitBreaker {
  private state: 'CLOSED' | 'OPEN' | 'HALF_OPEN' = 'CLOSED';
  private failures = 0;
  private successes = 0;
  private openedAt = 0;

  constructor(private config: CircuitBreakerConfig) {}

  async execute<T>(fn: () => Promise<T>, fallback: () => T): Promise<T> {
    if (this.state === 'OPEN') {
      if (Date.now() - this.openedAt >= this.config.waitDurationInOpenState) {
        this.state = 'HALF_OPEN';
      } else {
        return fallback();  // 熔断中，返回降级结果
      }
    }

    try {
      const result = await fn();
      this.onSuccess();
      return result;
    } catch (error) {
      this.onFailure();
      if (this.state === 'OPEN') {
        return fallback();
      }
      throw error;
    }
  }

  private onSuccess() {
    this.successes++;
    if (this.state === 'HALF_OPEN') {
      this.state = 'CLOSED';  // 试探成功，关闭熔断
      this.reset();
    }
  }

  private onFailure() {
    this.failures++;
    const total = this.failures + this.successes;
    if (total >= this.config.minimumNumberOfCalls) {
      const rate = (this.failures / total) * 100;
      if (rate >= this.config.failureRateThreshold) {
        this.state = 'OPEN';
        this.openedAt = Date.now();
      }
    }
  }

  private reset() {
    this.failures = 0;
    this.successes = 0;
  }
}
```

## 五、降级：有损服务胜过无服务

### 5.1 降级策略

```
降级原则：核心链路保住，非核心功能可牺牲

按层级降级：
1. 读降级：读缓存 / 读历史数据 / 返回兜底数据
2. 写降级：同步写转异步写 / 写入消息队列延迟处理
3. 功能降级：关闭非核心功能（推荐系统、评论、分享）
4. 数据降级：返回精简数据（只返回核心字段）
```

### 5.2 常见降级场景

```
┌──────────────────┬───────────────────────────┬──────────────────────┐
│       场景       │         正常流程          │      降级方案        │
├──────────────────┼───────────────────────────┼──────────────────────┤
│ 商品详情页       │ 实时查数据库              │ 读缓存（允许短时不一致）│
│ 搜索结果         │ ES 全文检索               │ 数据库 LIKE 模糊匹配  │
│ 推荐列表         │ 推荐算法实时计算          │ 返回热门/排行榜数据   │
│ 图片验证码       │ 生成动态验证码            │ 降级为短信验证码      │
│ 评论功能         │ 实时展示评论              │ 隐藏评论区            │
│ 支付结果通知     │ 实时推送                  │ 轮询查询              │
│ 日志记录         │ 同步写数据库              │ 写入消息队列异步处理  │
│ 数据导出         │ 实时生成文件              │ 异步生成 + 邮件通知   │
└──────────────────┴───────────────────────────┴──────────────────────┘
```

## 六、超时与重试

### 6.1 超时设置

```
超时是系统稳定性的底线——不设置超时 = 允许无限等待 = 资源泄漏

超时设置原则：

1. 每一层都要设置超时
   - HTTP 调用：connect timeout + read timeout
   - 数据库查询：statement timeout
   - Redis 调用：socket timeout
   - RPC 调用：request timeout

2. 超时时间参考 P99 延迟
   - 正常 P99 = 200ms → 超时设为 1000ms（3~5 倍 P99）
   - 不要设得太短（大量超时）也不要太长（失去保护意义）

3. 上游超时 > 下游超时
   - 网关超时 30s > 服务 A 超时 10s > 服务 B 超时 5s > DB 超时 3s
   - 否则下游还在处理，上游已经超时放弃，白白浪费资源
```

```typescript
// HTTP 客户端超时配置示例（axios）
const client = axios.create({
  timeout: 5000,             // 总超时 5 秒
  // 或更细粒度
  // adapter 中控制 connect / read / write 超时
});

// 数据库超时（MySQL）
// SET SESSION max_execution_time = 3000;  -- 查询超过 3 秒自动终止

// Redis 超时
const redis = new Redis({
  host: '127.0.0.1',
  port: 6379,
  connectTimeout: 3000,     // 连接超时 3 秒
  commandTimeout: 2000,     // 命令超时 2 秒
});
```

### 6.2 重试策略

```
重试的三条铁律：

1. 只有幂等操作才能重试
   - GET 请求 → 可以重试
   - PUT 请求 → 可以重试（幂等）
   - POST 请求 → 默认不重试（非幂等），除非保证幂等
   - DELETE 请求 → 可以重试（幂等）

2. 重试必须有退避（Backoff）
   - 固定间隔重试 → 可能加重下游负担
   - 指数退避（Exponential Backoff）+ 抖动（Jitter）

3. 重试次数有限
   - 一般 2~3 次，不超过 5 次
   - 重试次数过多说明不是临时故障，应该熔断
```

```
指数退避 + 抖动：

重试间隔 = min(baseInterval * 2^attempt + random_jitter, maxInterval)

示例（baseInterval=100ms, maxInterval=5000ms）：
第1次重试：100ms  + random(0~50ms)  ≈ 120ms
第2次重试：200ms  + random(0~100ms) ≈ 250ms
第3次重试：400ms  + random(0~200ms) ≈ 500ms
第4次重试：800ms  + random(0~400ms) ≈ 1000ms
第5次重试：1600ms + random(0~800ms) ≈ 2000ms

抖动（Jitter）的作用：
防止多个客户端在同一个时刻同时重试（Thundering Herd 惊群效应）
```

### 6.3 幂等设计

```
幂等：同一操作执行一次和执行多次的效果相同

幂等方案：

1. 唯一请求 ID（Idempotency Key）
   - 客户端生成唯一 ID，服务端根据 ID 去重
   - 适用于：支付、订单创建、数据写入

2. 数据库唯一约束
   - 利用 UNIQUE INDEX 防止重复插入
   - INSERT IGNORE / ON DUPLICATE KEY UPDATE

3. 乐观锁（版本号）
   - UPDATE ... SET version = version + 1 WHERE version = #{oldVersion}
   - 适用于：状态变更、数据更新

4. 状态机
   - 只允许合法的状态转换
   - UPDATE orders SET status = 'paid' WHERE id = #{id} AND status = 'pending'
   - 重复执行时 status 已不是 pending，影响行数为 0
```

```sql
-- 幂等表：记录每个请求 ID 的处理结果
CREATE TABLE idempotent_record (
    id VARCHAR(64) PRIMARY KEY COMMENT '幂等键（请求唯一ID）',
    result TEXT COMMENT '处理结果（JSON）',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expire_at DATETIME NOT NULL COMMENT '过期时间'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='幂等记录';

-- 处理流程：
-- 1. 收到请求，获取 idempotency_key
-- 2. 查询 idempotent_record 是否已存在
-- 3. 存在 → 直接返回之前的结果
-- 4. 不存在 → 执行业务逻辑 → 写入 idempotent_record → 返回结果
```

## 七、容灾设计

### 7.1 冗余

```
冗余是容灾的基础——任何单点都是潜在故障点

冗余层级：
1. 应用层冗余：多实例部署（至少 2 个实例）
2. 负载均衡：Nginx / 云 SLB，流量分发到多个实例
3. 数据库冗余：主从复制，读写分离
4. 缓存冗余：Redis Sentinel / Cluster
5. 机房冗余：同城双活 / 异地多活
```

### 7.2 隔离

```
隔离原则：不让一个故障影响其他部分

隔离维度：

1. 线程池隔离
   - 不同业务使用独立的线程池
   - 一个业务的慢请求不会耗尽全局线程池

2. 连接池隔离
   - 不同服务/数据库使用独立的连接池

3. 资源隔离
   - 核心业务和非核心业务使用不同的数据库实例
   - 大客户和小客户使用不同的资源池

4. 机房隔离
   - 不同业务部署在不同机房
   - 一个机房故障不影响其他业务

5. 租户隔离
   - 多租户系统中，不同租户的资源互不影响
```

```typescript
// 线程池隔离示例（伪代码）
// 不同业务使用独立的 HTTP 客户端和连接池

// 核心订单服务
const orderClient = axios.create({
  timeout: 3000,
  maxConcurrent: 50,     // 核心服务分配更多资源
});

// 非核心推荐服务
const recommendClient = axios.create({
  timeout: 5000,
  maxConcurrent: 10,     // 非核心服务限制并发
});

// 如果推荐服务不可用，不会影响订单服务的连接池
```

## 八、可观测性：发现故障的眼睛

### 8.1 三大支柱

```
可观测性 = 日志（Logs）+ 指标（Metrics）+ 链路追踪（Traces）

┌─────────────┬──────────────────┬──────────────────┐
│    日志     │      指标        │    链路追踪      │
├─────────────┼──────────────────┼──────────────────┤
│ 事件记录    │ 聚合数据         │ 请求完整路径     │
│ 谁在何时做了│ 系统运行状态     │ 调用了哪些服务   │
│ 什么       │ QPS/延迟/错误率  │ 每段耗时多少     │
│             │                  │                  │
│ ELK/Loki   │ Prometheus/Grafana│ Jaeger/Zipkin   │
│            │                  │ SkyWalking       │
└─────────────┴──────────────────┴──────────────────┘

关系：
- 指标发现问题（错误率上升了）
- 链路定位位置（是哪个服务慢）
- 日志查明原因（具体的错误信息）
```

### 8.2 关键指标（RED 原则 + USE 原则）

```
RED 原则（请求驱动型服务）：
- Rate：请求速率（QPS / TPS）
- Errors：错误率（HTTP 5xx 比例）
- Duration：延迟分布（P50 / P90 / P99 / P999）

USE 原则（基础设施资源）：
- Utilization：使用率（CPU 80%+ 需要关注）
- Saturation：饱和度（队列长度、等待线程数）
- Errors：错误数（网络丢包、磁盘 IO 错误）

必须监控的指标：
┌──────────────────────────────────────────────────┐
│ 应用层：QPS、延迟 P99、错误率、活跃连接数        │
│ 数据库：QPS、慢查询数、连接池使用率、主从延迟     │
│ 缓存：命中率、QPS、内存使用率、驱逐数             │
│ MQ：消息堆积量、消费延迟、生产/消费速率           │
│ 系统：CPU、内存、磁盘 IO、网络带宽、TCP 连接数    │
│ 业务：订单量、支付成功率、核心接口可用率           │
└──────────────────────────────────────────────────┘
```

### 8.3 告警设计

```
告警设计原则：

1. 告警要有价值——每个告警都需要人工处理
   ❌ CPU > 50% 告警（太灵敏，频繁误报）
   ✅ CPU > 85% 持续 5 分钟告警（有意义的阈值）

2. 分级告警
   P0（紧急）：核心功能不可用 → 电话 + 短信
   P1（严重）：功能受损但有降级 → 短信 + IM
   P2（警告）：指标异常但未影响用户 → IM 通知
   P3（提示）：需要关注但不需要立即处理 → 邮件

3. 告警收敛
   - 同一服务同一指标在短时间内只告警一次
   - 相关联的告警合并通知
   - 值班轮转，避免告警疲劳

4. 告警条件示例
   - 错误率 > 1% 持续 3 分钟 → P1
   - P99 延迟 > 3s 持续 5 分钟 → P2
   - 服务实例数 < 最小实例数 → P0
   - 数据库连接池使用率 > 90% → P1
   - 消息堆积 > 10000 条 → P2
```

### 8.4 健康检查

```typescript
// 健康检查端点（/health）

// Liveness Probe（存活探针）：进程是否还活着
// → 失败则重启容器
app.get('/health/live', (req, res) => {
  res.json({ status: 'UP' });
});

// Readiness Probe（就绪探针）：是否准备好接收流量
// → 失败则从负载均衡中摘除
app.get('/health/ready', async (req, res) => {
  const checks = {
    db: await checkDatabase(),
    redis: await checkRedis(),
    mq: await checkMessageQueue(),
  };

  const allHealthy = Object.values(checks).every(v => v === 'UP');
  res.status(allHealthy ? 200 : 503).json({
    status: allHealthy ? 'UP' : 'DOWN',
    checks,
  });
});
```

## 九、发布安全

### 9.1 灰度发布

```
灰度策略：

1. 金丝雀发布（Canary）
   → 新版本部署到 1 个实例
   → 观察 5~15 分钟，指标正常则继续扩大范围
   → 1% → 10% → 50% → 100%

2. 按用户维度灰度
   → 先对内部员工开放
   → 再对 1% 用户开放
   → 逐步扩大到 100%

3. 按地域灰度
   → 先在一个地区发布
   → 验证没问题后全国发布

4. A/B 测试
   → 新旧版本同时运行
   → 对比核心指标，决定全量哪个版本
```

### 9.2 回滚策略

```
回滚是最后的兜底——必须保证随时可以回滚

回滚原则：
1. 每次发布前确认回滚方案
2. 数据库变更必须向前兼容（先加新列，下个版本再删旧列）
3. 回滚操作 ≤ 5 分钟完成
4. 回滚后验证核心功能正常

数据库变更的兼容性：
┌──────────────┬──────────────────────────────────────┐
│    变更类型   │              兼容策略                 │
├──────────────┼──────────────────────────────────────┤
│ 新增列       │ 设默认值，新代码先上线再建列           │
│ 删除列       │ 先在代码中移除引用，下个版本再删列     │
│ 改列类型     │ 新增列 → 迁移数据 → 切换引用 → 删旧列 │
│ 改列名       │ 同"改列类型"，逐步迁移                 │
│ 新增索引     │ 用 pt-online-schema-change 避免锁表   │
└──────────────┴──────────────────────────────────────┘
```

### 9.3 Feature Flag

```
Feature Flag 的作用：
- 代码合并到主干但不开放功能 → 降低分支管理成本
- 出问题时一键关闭功能 → 不需要回滚整个版本
- 灰度控制 → 按百分比/用户群控制功能开放

实现方案：
1. 简单方案：配置中心（Nacos / Apollo）的开关
2. 中等方案：数据库 feature_flag 表
3. 专业方案：LaunchDarkly / Unleash / Flipt
```

## 十、故障恢复

### 10.1 应急预案（Runbook）

```
Runbook 是故障发生时的操作手册——慌乱时按步骤执行

Runbook 模板：

【故障名称】：支付接口超时
【故障等级】：P0
【触发条件】：支付接口 P99 > 5s 持续 3 分钟
【影响范围】：所有用户无法完成支付

【处理步骤】：
1. 确认故障
   □ 查看 Grafana 支付看板，确认错误率/延迟
   □ 检查支付服务实例数和健康状态
   □ 检查数据库连接池和慢查询

2. 止血
   □ 如果是突发流量 → 启动限流（配置中心修改限流阈值）
   □ 如果是下游超时 → 启动降级（返回"支付繁忙请稍后"）
   □ 如果是数据库问题 → Kill 慢查询，必要时主从切换

3. 恢复
   □ 根因修复后，逐步关闭降级/限流
   □ 观察指标 15 分钟，确认稳定

4. 复盘
   □ 24 小时内产出故障复盘报告
```

### 10.2 混沌工程

```
混沌工程：主动注入故障，验证系统的容灾能力

注入场景：
1. 杀掉一个服务实例 → 验证负载均衡是否能摘除并转移流量
2. 模拟网络延迟 → 验证超时和重试是否生效
3. 模拟数据库故障 → 验证降级是否触发
4. 模拟 Redis 宕机 → 验证缓存降级方案
5. 模拟磁盘满 → 验证监控告警和自动清理

工具：
- Chaos Mesh（Kubernetes）
- Chaos Monkey（Netflix）
- LitmusChaos

原则：
1. 先在测试环境做，再在生产环境做
2. 从小范围开始（一个实例）→ 逐步扩大
3. 每次实验有明确的假设和验证指标
4. 随时可以停止实验（一键恢复）
```

### 10.3 故障复盘

```
故障复盘模板（ blameless — 不追责，找根因）：

1. 故障概述
   - 时间、持续时长、影响范围、影响用户数

2. 时间线
   - HH:MM 告警触发
   - HH:MM 开始排查
   - HH:MM 定位根因
   - HH:MM 止血完成
   - HH:MM 完全恢复

3. 根因分析（5 Whys）
   - 为什么支付接口超时？→ 数据库慢查询
   - 为什么有慢查询？→ 新发布的报表导出功能没有加索引
   - 为什么没有加索引？→ Code Review 没有检查 SQL
   - 为什么 Review 没检查？→ 没有 SQL Review 的检查清单
   - 为什么没有检查清单？→ 缺少规范 → 【改进项：建立 SQL Review 规范】

4. 改进措施
   - 短期：给报表查询加索引
   - 中期：建立 SQL Review 检查清单
   - 长期：引入 SQL 审计工具自动检测

5. 验证
   - 每项改进措施有负责人和截止日期
```

## 十二、局限性与边界

```
稳定性建设的局限：

1. 无法做到 100% 可用
   - SLA 99.99% = 每年允许 52 分钟故障
   - 追求越高，成本指数级增长
   - 根据业务重要性设定合理的 SLA 目标

2. 稳定性 ≠ 安全性
   - 限流/熔断解决不了 SQL 注入、XSS 等安全问题
   - 两套体系需要并行建设

3. 过度防护的成本
   - 限流太严 → 用户体验差（正常请求被拒绝）
   - 降级太多 → 功能缩水，用户不满
   - 监控太多 → 告警疲劳，真正的问题被淹没

4. 分布式系统的固有复杂性
   - 网络分区（CAP 定理）
   - 分布式事务
   - 时钟同步
   - 这些问题没有"银弹"，只能权衡

5. 人的因素
   - 再好的系统也挡不住误操作
   - Runbook 再完善，慌乱时也可能执行错
   - 自动化 > 文档化 > 人工操作
```

```
稳定性 Review 要点：

□ 是否有限流？限流粒度是否合理？
□ 下游调用是否有熔断机制？
□ 非核心功能是否有降级方案？
□ 数据库变更是否向前兼容？
□ 新增 SQL 是否有慢查询风险？
□ 关键操作是否有日志记录？
□ 核心指标是否有监控和告警？
□ 发布是否有灰度策略？
□ 回滚方案是否确认？
□ 是否有对应的 Runbook？
```
